## 1. 项目概述

### 1.1 项目背景

企业知识中枢是一个面向中型及以上企业的内部智能知识平台，目标打通散落在各个业务系统的孤岛数据，让员工用自然语言提问，获得精准、可溯源、受权限管控的答案。项目分 P1/P2/P3 三个阶段迭代交付。

### 1.2 整体评估

| 维度 | 评估 |
|------|------|
| 核心功能完整性 | ✅ 智能问答、知识管理、权限管控三大核心链路均已跑通 |
| 架构扩展性 | ✅ 事件驱动 + 模块化 Maven 结构，新增模块成本低 |
| 性能与鲁棒性 | ⚠️ 大数据量同步、聚合查询等场景存在明显短板 |
| 需求与实现的吻合度 | ⚠️ 有 4 处关键需求在落地时出现偏差或降级 |

## 2. 需求落地偏差分析

以下对照《软件需求规格说明书》各章节，梳理需求在实现时出现的偏差。

### 偏差 1：PDF 表格结构化保留 — 需求落地为空实现

| 维度 | 说明 |
|------|------|
| **SRS 对应章节** | §5.3.3 表格结构化保留 |
| **SRS 原文要求** | "PDF 和 Word 中的表格，提取时保留为 Markdown 表格格式，而非打乱成无结构的文本。" |
| **实际落地情况** | `PdfParser.extractTablesAsMarkdown()` 方法返回 `null`，为**空实现**。PDFBox 的 `PDFTextStripper.setSortByPosition(true)` 仅按坐标排序输出文本，表格单元格被线性化为无序文本，列关系完全丢失。 |
| **影响范围** | 所有含表格的 PDF 文档在切片后表格语义破碎，检索时无法正确理解行列对应关系。 |
| **根因** | P2 阶段排期紧张，PDF 表格提取未找到合适的 Java 库（tabula-java 未引入），临时留空占位，后续 P3 未纳入开发计划。 |
| **补救方案** | 已记录于 `doc/未来补充/PDF带表格的结构保留切片方案.md`，提出三层策略：①引入 tabula-java 实现表格提取 ②引入 `[TBL]` 结构化标记 ③增强 TextSplitter 做表格感知切片。 |
| **当前状态** | ⚠️ 待实施 |

### 偏差 2：结构化条件过滤 — LLM 自动提取未启用

| 维度 | 说明 |
|------|------|
| **SRS 对应章节** | §5.1.4 结构化条件查询 |
| **SRS 原文要求** | "系统能理解数值、日期等精确条件的查询，不只是模糊语义搜索。"示例："月薪大于 1 万的研发部员工有哪些？" |
| **实际落地情况** | `StructuredFilterService` 和 `ChunkStructuredFilterMapper` 已实现 SQL 层的基础过滤能力，但 `FilterConditionExtractor`（LLM 自动从自然语言提取过滤条件）**未实现**。用户无法直接用自然语言触发结构化过滤，需依赖人工预先配置的字段映射。 |
| **影响范围** | 精确查询类问题（数值范围、日期区间、枚举匹配）实际走的是语义检索而非 SQL 精确过滤，结果精度和完整性无法保证。 |
| **根因** | 该功能依赖 `kb_chunk_structured` 表中有实际的结构化数据（来自 ETL 管道），而 ETL 数据同步在 P2 阶段才初步跑通，结构化字段覆盖不充分。LLM 提取本身也增加了延迟和出错风险，团队选择保守策略：先完成 SQL 过滤基础设施，LLM 提取留待数据积累后灰度开启。 |
| **补救方案** | 已记录于 `doc/未来补充/结构化字段过滤SQL-LLM自动提取启用方案.md`，设计了完整的 `FilterConditionExtractor` 组件 + 降级策略 + 灰度验证方案，默认 `enabled: false`。 |
| **当前状态** | ⚠️ 待实施（基础设施已就绪，LLM 提取组件待开发） |

### 偏差 3：RAG 聚合查询截断 — 列举/统计类查询结果不完整

| 维度 | 说明 |
|------|------|
| **SRS 对应章节** | §5.1.1 自然语言搜索（含结构化条件查询场景） |
| **SRS 原文要求** | "精确查询场景：月薪大于 1 万的研发部员工有哪些？" —— 隐含要求是返回**全部**匹配结果，而非 Top-K 截断。 |
| **实际落地情况** | RAG 检索管道存在 4 层串行截断：`wideTopK=30` → `RRF 融合` → `finalTopK=15` → `Token 预算裁剪`。语义检索的"找最相关"逻辑与列举类查询的"列出所有"需求存在根本矛盾。用户问"公司有哪些人已经离职"，离职人数超过 15 人时系统只返回 15 人。 |
| **影响范围** | 所有列举型（"列出所有 X"）和统计型（"有多少 Y"）查询结果不完整，直接影响用户对系统能力的信任。 |
| **根因** | P1/P2 的检索架构设计围绕"语义相关性排序"展开，未预留聚合查询路径。设计阶段未区分"找最相关文档"和"列出全部匹配记录"两类查询的本质差异。 |
| **补救方案** | 已记录于 `doc/未来补充/RAG聚合查询截断问题解决方案.md`，提出三层递进方案：①短期配置调优（`finalTopK: 15→30`）②新增 `QueryIntentClassifier` + `AggregationQueryService` 聚合查询分支 ③长期 NL-to-SQL 直查。 |
| **当前状态** | ⚠️ 待实施 |

### 偏差 4：大数据源同步性能 — 10 万条耗时约 50 分钟

| 维度 | 说明 |
|------|------|
| **SRS 对应章节** | §5.2 多源数据接入 |
| **SRS 原文要求** | "增量同步"、"减少对源系统的性能影响"、"知识库数据保持准实时（不超过 30 分钟延迟）"。 |
| **实际落地情况** | 10 万条记录同步耗时 ~50 分钟，远超 30 分钟的准实时目标。瓶颈分布在四个环节：① `JdbcConnector` 全量 `SELECT *` 装入 `ArrayList`（200MB 内存风险）② `DataSyncEtlListener` 逐条 `chunkMapper.insert()`（60 万次 SQL 往返）③ `BatchEmbeddingService` 阻塞队列容量仅 2000 ④ ChromaDB 逐条 HTTP 写入。 |
| **影响范围** | 大数据源首次同步耗时不可接受，增量同步虽然有游标分页但上游全量加载逻辑未变。 |
| **根因** | P1/P2 阶段以功能验证为主，测试数据量小（< 1000 条），未进行大数据量压力测试。P2 的 ETL 管线设计围绕"逐条处理保证事务一致性"，未预留批量写入的扩展点。 |
| **补救方案** | 已记录于 `doc/未来补充/大数据源同步性能改造方案.md`，提出四管齐下：① JDBC 流式读取 ② ETL 批量写入 MySQL（1000 条/批）+ 事件驱动解耦向量化 ③ 队列容量 2000→10000 + 非阻塞降级 ④ ChromaDB `addAll()` 批量写入。预计总耗时从 50 分钟降至 6-8 分钟。 |
| **当前状态** | ⚠️ 待实施 |

## 3. 协作效率问题

### 问题 1：需求文档与任务拆分之间存在"翻译损耗"

**现象**：《软件需求规格说明书》中的业务需求描述详实（如 §5.3.3 明确要求"表格结构化保留为 Markdown 格式"），但落到 `p2-tasks` 的任务拆分时，该需求被简化为"PDF 解析增强"，`PdfParser.extractTablesAsMarkdown()` 只留了方法签名和 `return null` 占位，没有对应的验收标准约束。

**后果**：任务形式上"完成"了（代码编译通过），但需求实际上没有落地。这个偏差直到 P3 阶段才被发现并写入"未来补充"，错过了最佳修复窗口。

**教训**：需求到任务的拆分环节缺乏"需求追溯矩阵"（RTM），关键业务需求在任务化过程中被稀释或丢失。

---

### 问题 2：模块间接口约定靠"文档描述"而非"契约测试"

**现象**：P2 阶段的 5 个新增模块（datasource/etl/data-quality/catalog/compensation）之间通过事件驱动解耦，但事件字段定义、ETL 输出格式（`CanonicalRecord` 结构）、质检通过/阻断的判断标准等关键接口，仅在设计文档中用文字描述。开发过程中多次出现上下游字段名不一致、必填字段遗漏等问题，需要联调时反复对齐。

**后果**：集成联调阶段花费了大量时间在"字段名对不上""这个字段你传了吗"这类沟通上。大数据源同步性能问题也与批量子系统之间的接口约定不明确有关——生产者不知道消费者的处理能力上限。

**教训**：事件驱动的微服务架构中，事件 Schema 应该作为"一等公民"被管理，最好以共享的 Java 类 + JSON Schema 快照形式约定，并在 CI 中做兼容性检查。

## 4. 可复用的小组开发经验

### 经验 1：事件驱动管道每个环节必须定义"熔断降级锚点"

**背景**：本项目的数据处理管道采用了完整的事件驱动链：`DataSyncCompleted → DataQuality → DataQualityPassed → ETL → Embedding`。在开发过程中，我们逐步意识到链上任何一个环节出问题，不能让它"炸掉"整条链路。

**经验总结**：
- 每个事件消费者（Listener）必须有独立的 try-catch + 降级逻辑，**不能把异常抛给 Spring 事件总线**（默认行为是中断后续 Listener）
- 降级策略按场景分类设计：
  - **可恢复降级**：入死信队列（DLQ），定时重试（如 Embedding 服务暂时不可用）
  - **静默降级**：记录日志但继续（如统计埋点失败不影响主流程）
  - **阻塞降级**：阻断后续环节 + 告警通知人工介入（如质检阻断率超过阈值）
- 在 `application.yml` 中为每个降级策略提供开关配置，运维时可按环节灰度关闭

**适用场景**：任何多步骤异步处理管道（订单处理、数据同步、CI/CD Pipeline）。

---

### 经验 2：RAG 项目的检索架构必须从 Day 1 区分"语义查询"和"聚合查询"两条路径

**背景**：本项目在 P1/P2 阶段仅设计了语义检索管道（Embedding + BM25 → RRF → Rerank → Top-K），到 P3 阶段才意识到列举/统计类问题需要完全不同的检索策略。如果在架构设计阶段就预留两条检索路径，可以避免大量的返工。

**经验总结**：
- 在检索入口处增加一个轻量级的**查询意图分类器**（规则匹配优先，LLM 兜底）：
  - **语义类**（"XX 流程是什么"）：走 HybridRetriever → Rerank → Top-K
  - **聚合类**（"列出所有 XX"、"有多少 YY"）：走 SQL 过滤 → 全量取回 → 紧凑格式化
- 两条路径共享 `FilterConditionExtractor`（从 NL 提取结构化条件），但下游分叉：
  - 语义路径用过滤条件缩小候选集（加 `LIMIT 500`）
  - 聚合路径用过滤条件做精确匹配（去掉 `LIMIT`，加安全上限 2000）
- 聚合路径的上下文构建需要用**紧凑格式**（如 JSON 数组）替代完整文本，Token 密度提升 5 倍以上

**适用场景**：所有基于 RAG 的知识库问答系统。

---

### 经验 3：性能验证必须纳入每个阶段的 Definition of Done

**背景**：大数据源同步性能问题（10 万条 ~50 分钟）的根因不是代码写错了，而是 P1/P2 阶段的测试数据量太小（< 100 条），无法暴露批量处理瓶颈。如果在 P2 的 DoD 中包含了"10000 条数据的同步耗时 ≤ 5 分钟"的性能基准，这些问题完全可以在阶段内发现和修复。

**经验总结**：
- 每个阶段发布前，必须跑一组**性能冒烟测试**（Smoke Performance Test）：
  - 知识库模块：100 份文档（含 PDF/DOCX/CSV）批量上传 + 检索延迟
  - 数据源模块：10000 条 JDBC 数据同步全链路耗时
  - RAG 模块：100 并发问答的 P95 延迟
- 性能基准值不需要很精确（允许 ±50% 浮动），但必须有——目的是**及时发现量级退化**，而不是追求精确的 SLA
- 性能测试用例纳入 CI 流水线（但不阻塞 PR merge），以报告形式展示趋势图
- 对批量处理类代码，Code Review 时强制检查：**是否存在"逐条处理"模式？能否改为批处理？**

**适用场景**：所有涉及批量数据处理的系统（ETL、消息消费、报表生成）。

## 5. 总结与展望

### 5.1 做得好的

- **模块化 Maven 结构**：从 P1 的 7 个模块到 P2 的 12 个模块，增量演进平滑，模块职责清晰
- **事件驱动解耦**：`DataSyncCompleted → DataQuality → ETL → Embedding` 事件链设计合理，新增 compensation 模块时无需修改上游代码
- **技术文档沉淀**：4 份"未来补充"方案文档质量高，问题诊断有根因分析，解决方案有完整的伪代码和验证方案，极大降低了后续修复的启动成本

### 5.2 需要改进的

- **需求追溯**：建立 RTM（需求追溯矩阵），确保 SRS 中的每个关键需求都有对应的开发任务和验收用例
- **集成测试前置**：在模块级别增加 Contract Test（契约测试），减少联调时的接口对齐成本
- **性能基准**：将性能冒烟测试纳入 DoD，避免"小数据量跑通 = 功能完成"的假象

### 5.3 下一步行动

| 优先级 | 行动项 | 依据 |
|--------|--------|------|
| P0 | 实施 RAG 聚合查询截断修复（偏差 3） | 直接影响用户对系统"能否列出全部结果"的信任 |
| P0 | 实施大数据源同步性能改造（偏差 4） | 阻塞生产环境大数据量接入 |
| P1 | 实施 PDF 表格结构化保留（偏差 1） | 影响含表格 PDF 的检索质量 |
| P1 | 灰度开启 LLM 结构化过滤提取（偏差 2） | 等 `kb_chunk_structured` 数据积累后启用 |
