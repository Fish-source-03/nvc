# 修复任务清单 — 总览与执行规则

> **来源**：`doc/问题清单/`（43 份问题文档） + 跨问题干扰分析
> **创建日期**：2026-10-06
> **组织方式**：按**修复批次**（而非按模块）——因为顺序约束与回退风险是本清单的核心价值
> **覆盖范围**：全部 43 个问题
> **用法**：主 agent 按批次顺序派发；每个 batch 文件可直接作为子 agent 的指令

## 一、为什么按批次而不是按模块

核查中发现，这 43 个问题之间存在五类相互干扰：

| 干扰类型 | 含义 | 后果 |
|---|---|---|
| **回退** | 后修的问题破坏前修的效果 | 前面的工作白做 |
| **陷阱** | 单独修 A 会让运行状态比不修更差 | 越修越糟 |
| **前置** | A 不修，B 修了也无效或出错 | 改了个寂寞 |
| **放大** | 修 A 后 B 的隐蔽缺陷变成常态 | 问题更难发现 |
| **重叠** | A、B 改同一方法，分两次改互相覆盖 | 二次返工 |

因此**不允许按问题编号顺序逐个修**，必须按批次与批次内顺序执行。

## 四、三条必须遵守的硬约束

这三条是"修了反而更糟"的陷阱，任何执行者都不得绕过：

### 硬约束 1：批次 01 必须整体完成，不得只做一半

- 只修 01（加 `@EnableScheduling`）而不修 02 → DLQ 空壳被周期性调用，**消息被误删**，比"不跑"更糟。
- 只修 02 而不修 01 → 定时器不跑，重试体永不执行，改动无效果。
- **01 与 02 必须同批交付。任务 1.3（开启定时器）必须在 1.1、1.2 完成后执行。**

### 硬约束 2：批次 02 中，任务 2.1 必须先于 2.3

- 先修 2.3（加 `@Transactional(readOnly=true)`）→ 查询真正路由到读库 → 而读库地址仍是硬编码 `localhost:3308` → **所有查询失败**。
- **2.1 完成并验证读库可覆盖/可达后，才能执行 2.3。**

### 硬约束 3：批次 03 中，任务 3.2（07）必须先于 3.3（06）

- 先修 06（`hasRole('ADMIN')`）→ 而 07 未修时用户刷新一次令牌 role 变成 `"user"` → **管理员被自己的修复锁在门外**。
- **07 必须先于或与 06 同一提交完成。**

## 五、给子 Agent 的通用指令模板

```
你是 agent-qr 项目的修复执行者。请严格按 doc/修复-tasks/batch-NN-xxx.md 执行。

硬性要求：
1. 只修改该 batch 文件「涉及文件」章节列出的文件，不得触碰其他文件。
2. 严格按 batch 文件内的任务顺序执行，不得调整顺序。
3. 每个任务都必须配套补充自动化测试（见 README 第七节）。
4. 完成后逐条核对「验收标准」，并给出证据（文件:行号 或 命令输出）。
5. 若发现需要修改 batch 范围外的文件，停下来报告，不要自行扩大范围。
6. 不输出任何 API Key、Token、密码、连接串原文。
7. 修改前先阅读该任务对应的 doc/问题清单/NN-xxx.md，理解原缺陷的完整上下文。

完成后按以下格式报告：
- 任务清单：逐条列出 完成 / 未完成 / 阻塞
- 验收证据：每条验收标准 + 实际验证方式
- 新增测试：测试类名 + 覆盖的用例 + 运行结果
- 意外的发现：执行中发现的、超出任务范围的观察
- 未完成项的原因
```

## 七、测试要求（所有批次强制）

**每个修复任务都必须配套补充自动化测试。** 这是本次修复与以往最大的不同——问题清单中大量缺陷属于"代码看起来对、运行时不对"，只有测试能拦截。

### 强制执行规则

1. **每个任务至少 1 条用例**，覆盖该缺陷的"修复前会失败、修复后会通过"的场景。
2. 测试应写在对应模块的 `src/test/java` 下（当前全部模块无此目录，需新建）。
3. 用例命名应直接反映缺陷语义，例如：
   - `listUsers_shouldReturn403_whenUserIsNotAdmin`
   - `refresh_shouldPreserveAbacAttributes`
   - `unknownEventType_shouldNotBeDeletedFromDlq`
4. 提交报告时需附测试类名、覆盖用例、运行结果。
5. **若某任务确实难以自动化测试**（如纯文档回填、部署配置），需在报告中说明理由，不得静默跳过。

### 测试基础设施

批次 01 的**任务 1.0** 负责建立测试基础设施，是其他批次补测试的前提。若其他批次先启动，应先做非测试部分的改动，待 1.0 完成后再补测试。

## 八、执行原则

1. **每完成一个批次，更新 `progress.md`**，记录任务状态、验收证据、新增测试、遗留问题。
2. **每个批次完成后提交一次 git commit**，提交信息注明批次号，便于回退与定位。
3. **批次 03 与 04 完成后必须回归验证**其他批次的功能——这两批触及高频路径（鉴权、检索）。
4. **遇到 batch 文件未覆盖的新问题，停下来上报**，不要自行决策。
5. 本次核查为静态分析，**执行修复时应有完整的构建环境**；若无法编译或运行测试，必须在报告中明确说明。

## 九、批次验收的总体标准

一个批次视为完成，需同时满足：

- [ ] batch 文件内所有任务的验收标准逐条通过
- [ ] batch 文件内「禁止事项」无一被违反
- [ ] **每个任务都补充了自动化测试，且测试通过**
- [ ] 项目可编译（`mvn -q clean compile` 或等效命令）
- [ ] 未引入对 batch 范围外文件的修改
- [ ] `progress.md` 已更新
