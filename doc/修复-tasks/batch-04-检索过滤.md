## 任务 4.1 — 让 operator 生效（问题 20）

> 问题详情：`doc/问题清单/20-FilterCondition的operator字段从不生效.md`

- [ ] **4.1.1** 让 `dispatchCondition` 读取 `operator`
  - 当前只按 `fieldType` 分派，`condition.getOperator()` 全方法体未被调用
  - NUMBER 类型按操作符生成正确的比较语义：
    | operator | 语义 | 说明 |
    |---|---|---|
    | `OP_GT` | `(value, +∞)` | 开区间，需 SQL 用 `>` 而非 `>=` |
    | `OP_GTE` | `[value, +∞)` | |
    | `OP_LT` | `(-∞, value)` | 开区间 |
    | `OP_LTE` | `(-∞, value]` | |
    | 无 operator | `[minValue, maxValue]` | 维持现有区间语义 |
  - **先核对 `selectChunkIdsByNumberRange` 的 SQL**：若当前是 `BETWEEN`（闭区间），需评估是否新增支持开区间的方法

- [ ] **4.1.2** 补 operator 的合法性校验
  - 非法 operator 应显式报错（或记录 WARN 后按区间语义处理），**不应静默退化为等值查询**
  - 当前 `parseMinNumber` / `parseMaxNumber` 在 `minValue`/`maxValue` 均为 null 时都回退到 `value`，导致区间退化为 `[value, value]`

### 补充测试（**关键**）

- [ ] 用例：`OP_GT` + value=10000 → SQL 条件为 `> 10000`（而非 `= 10000`）
- [ ] 用例：`OP_LT` + value=5000 → SQL 条件为 `< 5000`
- [ ] 用例：`OP_GTE` / `OP_LTE` 的边界包含性正确
- [ ] 用例：无 operator 时维持区间语义
- [ ] 用例：非法 operator 的行为符合 4.1.2 的约定

### 验收标准

- [ ] `condition.getOperator()` 在分派逻辑中被读取
- [ ] 四种运算符的语义正确
- [ ] 上述测试全部通过

### 禁止事项

- ❌ 不要改变无 operator 时的现有区间语义（其他调用方可能依赖）
- ❌ 不要删除 `OP_*` 常量定义

## 任务 4.2 — 修正域过滤的空集守卫（问题 19）

> 问题详情：`doc/问题清单/19-检索域过滤在候选集为空时被静默跳过.md`

- [ ] **4.2.1** 把空候选集的处理从"跳过过滤"改为"返回空结果"
  - 当前守卫：`if (hasDomainFilter && !candidateChunkIds.isEmpty())` —— 空集时整个过滤块被跳过，**退化为全库检索**
  - 改为：`hasDomainFilter` 为真且候选集为空时，**直接返回空结果**
  - 依据：设计 §8.11.3 明确要求候选集为空时返回空

- [ ] **4.2.2** 补充可观测性
  - 该分支命中时应输出 **WARN 级**日志（当前 `log.debug` 在被跳过的块内，运行期完全静默）
  - 便于发现"某域长期无结构化数据"

- [ ] **4.2.3** 确认降级语义
  - 若业务上确实需要"域内无数据时回退全局"，必须作为**显式配置**存在，并在回答中提示用户"已扩大检索范围"
  - **默认按设计执行：返回空**，不做静默扩大

### 补充测试

- [ ] 用例：指定域且候选集为空时，检索结果为空列表（**不回退到全库**）
- [ ] 用例：指定域且候选集非空时，正常过滤
- [ ] 用例：未指定域时，行为不变（不做过滤，全库检索是设计预期）

### 验收标准

- [ ] 空候选集不再导致跨域返回
- [ ] 该分支有 WARN 级日志
- [ ] 上述 3 条测试通过

### 禁止事项

- ❌ 不要修改批次 03 任务 3.5 加入的**权限过滤**逻辑（那是另一层过滤，与本任务的域过滤并存）
- ❌ 不要移除 `hasDomainFilter` 判断（未指定域时不该过滤）
