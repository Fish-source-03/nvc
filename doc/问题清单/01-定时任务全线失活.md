# 01 · 定时任务全线失活（全仓库缺少 `@EnableScheduling`）

> **严重程度**：🔴 高
> **所属模块**：agent-qr-web（启动类）、影响 compensation / catalog / rag
> **设计依据**：《系统详细设计说明书》§7.1（DLQ 定时重试）、§10.1 决策 6（孤儿向量扫描兜底）、§8.15.6（域向量刷新）
> **核查日期**：2026-10-06
> **核查方式**：静态代码分析（未编译、未运行服务）

---

## 一、问题描述

Spring 的 `@Scheduled` 注解只有在配置类上存在 `@EnableScheduling` 时才会被注册为定时任务。本项目全仓库**没有任何一处** `@EnableScheduling`，启动类仅有 `@SpringBootApplication` 与 `@ComponentScan`。

结果是：代码中 5 处 `@Scheduled` 定时方法**在运行期完全不会执行**。这直接导致设计文档中多处"最终一致性兜底"承诺失效——DLQ 死信永不重试、孤儿向量永不扫描、重复数据永不清理、P3 语义路由的域向量永不刷新。

---

## 二、推断依据

### 依据 1：全仓库无 `@EnableScheduling`

```bash
grep -rn "EnableScheduling" --include=*.java .
# 输出为空（含已编译 .class 也无该字符串）
```

### 依据 2：启动类未开启定时任务支持

`agent-qr-web/src/main/java/org/example/agent_qr/AgentQrApplication.java:13-15`

```java
@SpringBootApplication
@ComponentScan("org.example.agent_qr")
public class AgentQrApplication { ... }
```

既无 `@EnableScheduling`，也无等价的 XML / `SchedulingConfigurer` 配置类（`grep SchedulingConfigurer` 同样零命中）。

### 依据 3：5 处 `@Scheduled` 因此全部失活

```bash
grep -rn "@Scheduled" --include=*.java .
```

| 失效任务 | 位置 | 设计文档要求 |
|---|---|---|
| DLQ 死信重试 | `agent-qr-web/.../web/scheduler/DlqRetryScheduler.java:44`（`fixedDelay = 30000`） | §7.1 指数退避重试 |
| 孤儿向量扫描 | `agent-qr-compensation/.../scanner/OrphanVectorScanner.java:60`（`fixedDelay = 300000`） | §10.1 决策 6（文档要求 30 分钟兜底） |
| 重复数据清理 | `agent-qr-compensation/.../scanner/DuplicateCleanupScanner.java:51`（`cron = "0 0 3 * * ?"`） | P3 运维能力 |
| 域描述刷新（catalog） | `agent-qr-catalog/.../router/DomainRouterV2.java:92`（`fixedRate = 300_000`） | §8.15.6 |
| 域向量刷新（rag） | `agent-qr-rag/.../router/DomainRouterV2.java:221`（`fixedRate = 300_000`） | §8.15.6 |

### 依据 4：仅有部分具备"自愈"能力，多数没有

- 有兜底：`catalog` 版 `DomainRouterV2` 的 `getDomainDescriptions()` 内含 `isStale()` 懒刷新（`DomainRouterV2.java:73-78`），即使定时器不跑也能在下次调用时刷新。
- 无兜底：`rag` 版 `DomainRouterV2.refreshDomainEmbeddings()`、`OrphanVectorScanner`、`DuplicateCleanupScanner`、`DlqRetryScheduler` 均**无懒加载入口**，一旦定时器不触发即永久不执行。

---

## 三、影响范围

1. **DLQ 兜底链路断裂**：设计 §7.1 承诺的"事件消费者失败 → 入 DLQ → 指数退避重试 → 耗尽转 DEAD"流程只剩"入队"和"表里有记录"，重试环节不存在（另见文档 02）。
2. **孤儿向量长期残留**：文档删除若 ChromaDB 物理删除失败，残留向量将永久污染检索结果，且无任何清理途径。
3. **P3 语义路由退化**：域向量建立后不再随目录结构变化更新，语义路由逐渐偏离实际业务域划分。
4. **复盘报告"经验 1"失效**：复盘报告把 DLQ 作为"可恢复降级锚点"作为核心经验阐述，该锚点当前在运行时不存在。

---

## 四、修复方向

1. 在启动类 `AgentQrApplication` 上添加 `@EnableScheduling`（最小改动，一行）。
2. 若出于分阶段启用的考虑有意关闭，应在 `application.yml` 中以 `@ConditionalOnProperty` 显式开关，并在设计文档 §9 中说明——而不是静默缺失。
3. 修复后需先解决文档 02 所述的"重试体为空壳"问题，否则定时器启动只会让空壳被周期性调用。

---

## 五、核查边界

- 本结论为静态分析。未编译、未启动服务，因此未观测到运行期日志。
- 已排除 XML 配置、`SchedulingConfigurer` 实现、以及第三方 starter 自动配置等替代开启方式（均已 grep 验证）。
- 运行期若通过外部依赖的 `@Configuration` 引入 `@EnableScheduling`，不在本仓库静态可查范围内。
