# 29 · 孤儿向量扫描存在结构性漏检

> **严重程度**：🟠 中高
> **所属模块**：agent-qr-compensation（OrphanVectorScanner、ChromaRetriever）
> **设计依据**：《系统详细设计说明书》§10.2 OrphanVectorScanner（孤儿向量扫描清理）、§10.1 决策 6
> **核查日期**：2026-10-06
> **核查方式**：静态代码分析（未编译、未运行）

---

## 一、问题描述

`OrphanVectorScanner` 被设计为"文档删除链路的最终一致性兜底"：当 MySQL 已删除但 ChromaDB 物理删除失败时，由它定期扫描并清理残留向量。

实际实现存在两个缺陷，且二者叠加使兜底**恰好失效在其唯一的应用场景上**：

1. **扫描方向反了**：设计是"ChromaDB → 对照 MySQL"（从向量库取全部 documentId，找出 MySQL 中已不存在的），实际是"MySQL 未删除切片 → 对照 ChromaDB"；
2. **输入查询排除了软删切片**：`selectAllReadyChunks` 的 SQL 带 `deleted = 0`，而删除流程**已先把切片软删**。因此在"MySQL 删成功、Chroma 删失败"这一失败态下，这些切片已被排除在扫描输入之外——**永远发现不了残留向量**。

此外，设计依赖的 `ChromaVectorStore.getAllDocumentIds()` 在项目的 `ChromaRetriever` 中**不存在**，即原设计的扫描方式在当前技术选型下无法直接实现。

---

## 二、推断依据

### 依据 1：扫描输入是"未删除的 READY 切片"

`agent-qr-compensation/src/main/java/org/example/agent_qr/compensation/scanner/OrphanVectorScanner.java:93`

```java
List<Chunk> chunks = chunkMapper.selectAllReadyChunks();
```

`agent-qr-knowledge/.../mapper/ChunkMapper.java:59` 对应的 SQL：

```sql
SELECT * FROM kb_chunk WHERE status = 'READY' AND deleted = 0
```

### 依据 2：删除流程会先软删切片

`agent-qr-compensation/.../listener/DocumentDeleteListener.java:58-61` 先执行 MySQL 逻辑删除（把 `deleted` 置 1），再执行 ChromaDB 物理删除。

因此"MySQL 删成功 + Chroma 删失败"的目标场景中，切片已经是 `deleted = 1`，**不在依据 1 的查询结果里**。

### 依据 3：设计与实现方向相反

§10.2 描述的扫描逻辑是"`chromaVectorStore.getAllDocumentIds()` → 对照 MySQL"，即从向量库侧驱动。

但 `agent-qr-rag/.../retriever/ChromaRetriever.java` 仅提供 `deleteByIds` / `deleteByDocumentId` / `deleteByMetadata` 三个删除方法（`:104`、`:134`、`:162`），**无 `getAllDocumentIds()`**。全仓检索该方法名零命中。

即：设计所需的能力在当前实现中不存在，实现者改为反向扫描——但改后的方向恰好漏掉了目标场景。

### 依据 4：清理计数虚高

`OrphanVectorScanner.java:100-107` 与 `:198-205` 在调用删除后**无条件 `cleaned++`**，而底层 `ChromaRetriever.deleteByDocumentId`（`:104-122`）与 `deleteByMetadata`（`:162-179`）内部 `catch` 后**不重抛**、store 为 null 时直接 `return`。

对照：`deleteByIds`（`:134-152`）是重抛异常的。因此孤儿清理这条路径的日志会显示"清理了 N 条"，实际可能一条都没删。

### 依据 5：定时器未启用

`OrphanVectorScanner.java:60` 的 `@Scheduled(fixedDelay = 300000)` 因缺少 `@EnableScheduling` 不会执行（见文档 01），且实际周期为 5 分钟，与设计 §10.1 决策 6 要求的 30 分钟不一致。

---

## 三、影响范围

1. **兜底能力实质为零**：该扫描器存在的唯一意义就是处理"MySQL 删了、Chroma 没删"的情况，而这正是它扫不到的。
2. **残留向量持续污染检索**：已删除文档的内容仍会被检索到并出现在回答中——用户视角是"删了还能搜到"。
3. **日志误导**：依据 4 使日志显示清理成功，掩盖了实际未清理的事实。
4. **与文档 01、02 叠加**：定时器不跑、DLQ 不重试、扫描器漏检——删除链路的**三重兜底全部失效**，仅剩主路径（`DocumentDeleteListener` 的同步删除）在工作。

---

## 四、修复方向

1. **改为设计所述的扫描方向**：在 `ChromaRetriever` 中补充"列出全部 documentId / chunkId"的能力（ChromaDB 的 `get()` API 支持按条件拉取 metadata），然后以向量库为驱动、对照 MySQL 的存在性。
2. **若坚持当前方向，则必须放宽输入查询**：改为扫描**包含**已软删切片（如 `deleted IN (0,1)` 或全量），再逐一校验 ChromaDB 中是否残留。当前写法在逻辑上自相矛盾。
3. **修正计数**：删除方法应向上抛出异常或返回删除条数，扫描器据实际结果计数；`ChromaRetriever` 内部的静默 `catch` 应至少返回 boolean。
4. **对齐调度周期**：`fixedDelay` 改回 30 分钟（或更新设计文档），并解决文档 01。
5. **补测试**：构造"MySQL 已软删 + Chroma 残留"的场景，验证扫描器能发现。

---

## 五、核查边界

- 静态分析，未运行扫描、未与 ChromaDB 交互。
- 未连接数据库确认当前是否存在孤儿向量残留（可通过对比 ChromaDB 向量总数与 `kb_chunk` 有效切片数来验证）。
- 未确认 ChromaDB 客户端库（langchain4j）提供哪些列举 API——影响修复方案 1 的可行性。
- 注意：`agent-qr-compensation/pom.xml:41-45` 声明了 `langchain4j-chroma` 依赖但全模块无 `ChromaVectorStore` 引用，即该依赖当前未被使用，修复时需先确认技术选型。
