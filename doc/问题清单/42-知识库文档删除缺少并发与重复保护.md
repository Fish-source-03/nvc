# 42 · 知识库文档删除缺少并发与重复保护

> **严重程度**：🟡 中
> **所属模块**：agent-qr-knowledge（DocumentCommandService）
> **设计依据**：《系统详细设计说明书》§5.2.1 `requestDeleteDocument`（状态为 DELETING 时应报错）
> **核查日期**：2026-10-06
> **核查方式**：静态代码分析（未编译、未运行）

---

## 一、问题描述

`requestDeleteDocument` 的删前校验只包含两项：文档存在性、ABAC 权限。**缺少设计文档要求的状态校验**——当文档已处于 `DELETING` 状态时，应直接报错拒绝，而非再次执行删除流程。

后果：重复点击删除、或前端重试、或并发请求时，会对同一文档**重复发布删除事件**，进而在补偿模块**重复创建 `DeleteTask`**、重复执行 ChromaDB 删除。由于删除链路本身缺少幂等设计（见文档 30、31），重复执行会污染任务表并使状态更难追踪。

---

## 二、推断依据

### 依据 1：当前实现的全部校验

`agent-qr-knowledge/src/main/java/org/example/agent_qr/knowledge/service/DocumentCommandService.java:86-115`

```java
@Transactional
public void requestDeleteDocument(Long documentId) {
    Document doc = documentMapper.selectById(documentId);
    if (doc == null) {
        throw new BusinessException(404, "文档不存在");
    }

    // ABAC 文档级检查
    UserPrincipal user = getCurrentUser();
    if (!abacEvaluator.canDeleteDocument(user, doc.getDomain(), doc.getSensitivityLevel())) {
        throw new AccessDeniedException("无权删除该文档");
    }

    // 标记 DELETING
    documentMapper.updateStatus(documentId, DocumentStatus.DELETING.name());

    // 收集关联信息
    List<Long> chunkIds = chunkMapper.selectByDocumentId(documentId).stream()
            .map(...::getId).toList();
    List<String> chromaIds = chunkMapper.selectChromaIdsByDocumentId(documentId);

    // 发布事件
    eventPublisher.publishEvent(event);
    ...
}
```

**没有对 `doc.getStatus()` 做任何判断**。即使文档已是 `DELETING`，也会再次执行：再次 `updateStatus(DELETING)` → 再次发布事件。

### 依据 2：设计文档的明确要求

《系统详细设计说明书》§5.2.1（说明书 1468-1470 行）的 `requestDeleteDocument` 伪码中，明确包含"若状态为 DELETING 则抛业务异常"的校验。

### 依据 3：下游缺少幂等保护

事件消费方 `agent-qr-compensation/.../listener/DocumentDeleteListener.java:58-74` 与 `DocumentDeleteServiceV2.java:47-83` 每收到一次事件就 `deleteTaskMapper.insert(task)` 一次——**无去重判断**。

因此重复事件会直接产生重复的 `delete_task` 记录。叠加文档 30（失败不落 FAILED）与文档 31（依赖为空时假成功），任务表的状态会变得难以解读。

### 依据 4：`@Transactional` 不能防止重复

方法上的 `@Transactional` 保证的是**单次执行**的原子性，无法阻止两次独立的请求各自开启事务并先后执行。并发场景下需要乐观锁（版本号）或状态条件更新（`UPDATE ... WHERE status != 'DELETING'`）。

---

## 三、影响范围

1. **重复任务与重复操作**：同一文档产生多条 `DeleteTask`，重复调用 ChromaDB 删除接口。
2. **状态语义混乱**：`delete_task` 表无法反映"这个文档的删除是否已完成"。
3. **前端体验**：用户重复点击删除不会得到"正在删除中"的反馈，界面行为不确定。
4. **掩盖其他缺陷**：重复执行会放大文档 30、31 的影响，使问题更难定位。

---

## 四、修复方向

1. **补状态校验**（最小改动）：
   ```java
   if (DocumentStatus.DELETING.name().equals(doc.getStatus())) {
       throw new BusinessException(409, "文档正在删除中，请勿重复操作");
   }
   ```
2. **补已删除校验**：`DELETED` 状态的文档同样应拒绝。
3. **并发安全**：仅靠读-判断-写存在竞态窗口。建议改用条件更新：
   ```sql
   UPDATE kb_document SET status = 'DELETING' WHERE id = #{id} AND status <> 'DELETING'
   ```
   并依据影响行数判断是否由本次请求成功抢占。
4. **下游幂等**：`DocumentDeleteServiceV2` 创建任务前可按 `documentId` 查重（需先补 `DeleteTaskMapper` 的查询方法——见文档 30）。
5. **前端配合**：删除后按钮应进入"删除中"状态并禁用，减少重复提交的入口。
