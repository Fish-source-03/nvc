# 35 · 质检规则页为本地假数据、无后端支撑

> **严重程度**：🟡 中
> **所属模块**：agent-qr-web-frontend（RulesManager）、agent-qr-data-quality
> **设计依据**：`doc/p3-prompt.md`（P3 质检规则管理）；后端《系统详细设计说明书》§8.8 未定义规则管理接口
> **核查日期**：2026-10-06
> **核查方式**：静态代码分析（未编译、未运行）

---

## 一、问题描述

前端存在一个质检规则管理页面 `/admin/quality/rules`，可增删改查"质检规则"。但该页面**完全依赖浏览器 localStorage**，没有任何后端接口支撑：

- 首次进入时写入 5 条硬编码的默认规则；
- 所有增删改只写回 localStorage；
- 代码注释明确写着"后续对接后端 API"。

后端 data-quality 模块仅有 `/reports` 两个查询端点，**没有任何规则相关的 CRUD 接口**。

后果：规则是每个浏览器各存一份的本地数据，不跨设备、不跨用户，**也不参与任何真实质检**——质检实际执行的是 `CompletenessRule` / `EncodingRule` / `FormatRule` / `DeduplicationRule` 四个 Java 类中写死的逻辑。

---

## 二、推断依据

### 依据 1：页面从 localStorage 读写

`agent-qr-web-frontend/src/views/quality/RulesManager.vue`

```
:98     // 从 localStorage 加载规则（后续对接后端 API）
:100    const saved = localStorage.getItem('quality-rules')
:104    // 默认规则（5 条硬编码）
:121    localStorage.setItem('quality-rules', JSON.stringify(rules.value))
```

代码注释已自述"后续对接后端 API"，即作者本人也认为该实现对未完成。

### 依据 2：后端无规则管理接口

`agent-qr-data-quality/.../controller/DataQualityController.java:45,61` —— 全类仅两个映射：

| 端点 | 方法 |
|---|---|
| `GET /api/dataquality/reports` | 查询质检报告列表 |
| `GET /api/dataquality/reports/{batchId}` | 查询质检报告详情 |

无规则相关的 GET/POST/PUT/DELETE。

### 依据 3：真实质检逻辑是 Java 硬编码

`agent-qr-data-quality/.../rule/` 下的四条规则（`CompletenessRule`、`EncodingRule`、`FormatRule`、`DeduplicationRule`）都是 Spring Bean，通过 `DataQualityChecker` 的 `List<QualityRule>` 注入执行。规则的可配置部分仅限于"关键字段列表"等少量参数（如 `CompletenessRule` 的字段列表可由数据源配置覆盖），**规则的增删改查不由前端页面驱动**。

### 依据 4：路由已注册但入口隐蔽

`src/router/index.ts:80-86` 注册了 `/admin/quality/rules`；入口仅在生产质量报告页的一个按钮（`QualityReportView.vue:120`）。因此该页面较难被发现，问题也未被反馈。

### 依据 5：全项目 TODO 检索的结果

`src/` 全目录检索 `TODO|FIXME|mock|假数据|写死|占位` **零命中**——本项目前端代码整体干净，本页是唯一一处"实现了但未接线"的功能（其注释用的是"后续对接"而非 TODO 标记，因此未被检索命中）。

---

## 三、影响范围

1. **用户被误导**：管理员在页面上配置的规则**不会生效**，且刷新/换设备后配置丢失。用户会以为系统按自己的配置在质检。
2. **功能不可达预期**：若 P3 验收标准包含"质检规则可配置"，该项未达成。
3. **实现成本沉没**：页面 UI 已完成，但后端接口、规则持久化表、规则动态加载机制都需要从零建设。

---

## 四、修复方向

1. **二选一，先明确需求**：
   - **方案 A（补齐后端）**：这是完整方案，需建设
     - `quality_rule` 表 + 实体/Mapper；
     - `DataQualityController` 的规则 CRUD 端点；
     - `DataQualityChecker` 从数据库动态加载规则（替代当前的 `List<QualityRule>` Bean 注入模式）；
     - 前端切换到真实 API。
     工作量较大，涉及质检引擎的核心改造（当前规则是编译期 Bean，动态化需要引入规则表达式或脚本引擎）。
   - **方案 B（移除页面）**：删除 `RulesManager.vue` 与路由，在后端规则实现处补充说明"规则为代码内置，不可在线配置"。成本低，且避免误导。
2. **若不打算近期实施，建议至少先加提示**：在页面上明确标注"规则管理为演示功能，配置暂不生效"。
3. **长期建议**：若确需动态规则，考虑用配置化的规则定义（字段 + 校验类型 + 阈值）而非任意脚本，降低复杂度。
