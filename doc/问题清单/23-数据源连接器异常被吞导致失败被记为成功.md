# 23 · 数据源连接器异常被吞导致失败被记为成功

> **严重程度**：🟠 中高
> **所属模块**：agent-qr-datasource（JdbcConnector、RestApiConnector、S3Connector）
> **设计依据**：《系统详细设计说明书》§8.7.2 JdbcConnector（异常应抛 `BusinessException`）
> **核查日期**：2026-10-06
> **核查方式**：静态代码分析（未编译、未运行）

---

## 一、问题描述

三个数据源连接器的 `fullSync` / `incrementalSync` 方法在捕获异常后**一律只记录日志，然后返回"部分或空结果"**，既不重抛异常，也不在返回值中标记失败。

调用方随后依据返回行数写入 `sync_record` 状态为 `SUCCESS`、并把数据源状态置为 `ACTIVE`。设计 §8.7.2 明确要求抛出 `BusinessException`。

后果：同步中途失败（连接中断、SQL 错误、权限不足等）在系统中表现为"**同步成功，0 行**"，运维与用户都无法感知。数据源长期同步不到数据，但看板上显示一切正常。

---

## 二、推断依据

### 依据 1：JdbcConnector 吞异常后返回部分结果

`agent-qr-datasource/src/main/java/org/example/agent_qr/datasource/connector/JdbcConnector.java:125-131`（全量）

```java
} catch (Exception e) {
    log.error("JDBC 全量同步失败: {}", e.getMessage(), e);
}

return new SyncResult(allRows.size(), allRows, ...);   // 异常后照常返回
```

`:191-195`（增量）为同一模式：

```java
} catch (Exception e) {
    log.error("JDBC 增量同步失败: {}", e.getMessage(), e);
}

return new SyncResult(allRows.size(), allRows, newCursor);
```

### 依据 2：RestApiConnector 与 S3Connector 同样

`RestApiConnector.java:50`、`:102`、`:139`；`S3Connector.java:147-149`、`:216-218` —— 均为 `catch (Exception e) { log.error(...) }` 后继续返回。

### 依据 3：设计文档要求抛异常

《系统详细设计说明书》§8.7.2（说明书 3532-3535 行）的示例代码中，异常处理为抛出 `BusinessException`，由上层决定降级或告警。

### 依据 4：调用方据返回行数记为成功

`SyncScheduler.java:145-161` 与 `DataSourceService.java:192-206` 在连接器返回后写入同步记录，未校验"是否发生异常"——因为异常信息已丢失（既未抛出，也未在 `SyncResult` 中携带错误标志）。

### 依据 5：`SyncResult` 无失败标志

`agent-qr-datasource/.../dto/SyncResult.java` 的字段为 `totalCount` / `records` / `nextCursor` 等，**没有 `success` / `errorMessage` 字段**，因此即便连接器想传递失败状态也无处可放。

---

## 三、影响范围

1. **静默数据丢失**：数据源同步失败 → 显示成功 → 无人排查 → 知识库长期缺数据。
2. **故障排查成本高**：唯一线索是应用日志中的一行 ERROR；日志轮转后无迹可寻（`dlq_message` 也不会记录，因为异常未传播到 DLQ 逻辑）。
3. **与文档 21 混淆**：性能问题与失败问题在表现上都是"数据没进来"，难以区分。
4. **同步记录表失真**：`sync_record` 表的数据不再可信，运维无法据此判断数据源健康状况。

---

## 四、修复方向

1. **连接器应向上抛出异常**（或返回带失败标志的结果）：
   - 方案 A（对齐设计）：按 §8.7.2 抛 `BusinessException`，由调用方决定是否入 DLQ；
   - 方案 B（更轻量）：给 `SyncResult` 增加 `success` / `errorMessage` 字段，连接器返回失败态，调用方据此写 `sync_record=FAILED`。
   建议 B，因为同步失败通常需要区分"部分成功"与"完全失败"，异常传播会丢失部分结果。
2. **记录应为 FAILED 而非 SUCCESS**：调用方需根据连接器返回的失败标志改写 `sync_record` 状态。
3. **接入 DLQ 或告警**：同步失败属可恢复降级场景，建议入 DLQ 并接入告警（注意需先解决文档 02 的 DLQ 重试空壳）。
4. **日志脱敏检查**：`JdbcConnector.java:51` 把完整 JDBC URL 写入日志，URL 可能内嵌凭据，建议改为脱敏输出。

---

## 五、核查边界

- 静态分析，未运行同步、未构造连接失败场景。
- 未连接数据库确认 `sync_record` 表中当前实际的状态分布（是否有大量"成功但 0 行"的记录——可作为本缺陷的验证手段）。
- 未检查 `S3Connector` 的分页读取是否有类似的静默截断（其 `listObjectsV2` 分页逻辑本身是完整的）。
