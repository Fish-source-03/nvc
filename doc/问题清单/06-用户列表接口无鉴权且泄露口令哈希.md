# 06 · 用户列表接口无鉴权且泄露口令哈希

> **严重程度**：🔴 高（安全缺陷）
> **所属模块**：agent-qr-auth（AdminController）、agent-qr-user（SysUser）、agent-qr-web（SecurityConfig）
> **设计依据**：《系统详细设计说明书》§3.2.12 路由表（`/api/admin/**` 应为 `hasRole("ADMIN")`）、§4.1.1（listUsers 权限 = ADMIN）
> **核查日期**：2026-10-06
> **核查方式**：静态代码分析（未运行服务、未实际发起请求）

---

## 一、问题描述

用户列表接口 `GET /api/admin/users` 存在两个叠加的安全缺陷：

1. **接口无任何权限校验**：Controller 方法上没有 `@PreAuthorize`，方法体内也没有手写的权限判断；全局路由规则只要求"已认证"。任何登录用户（包括角色为 `user` 的普通账号）都可以分页拉取全站用户数据。
2. **响应体包含 BCrypt 口令哈希**：接口返回 `Result<IPage<SysUser>>`，而 `SysUser.password` 字段没有 `@JsonIgnore`，全仓库也没有任何 `@JsonIgnore` 使用，因此口令哈希随 JSON 一并返回。

两者叠加构成**任一登录用户可批量导出口令哈希**的高危场景。获取哈希后可离线爆破，弱口令将被直接还原。

---

## 二、推断依据

### 依据 1：Controller 方法无权限校验

`agent-qr-auth/src/main/java/org/example/agent_qr/auth/controller/AdminController.java:74-84`

```java
@GetMapping("/users")
public Result<IPage<SysUser>> listUsers(
        @RequestParam(defaultValue = "1") Integer page,
        @RequestParam(defaultValue = "10") Integer size,
        @RequestParam(required = false) String keyword) {
    log.info("查询用户列表: page={}, size={}, keyword={}", page, size, keyword);
    Page<SysUser> pageParam = new Page<>(page, size);
    IPage<SysUser> result = sysUserMapper.selectPage(pageParam, keyword);
    return Result.success(result);
}
```

对比同类的其他方法（如 `createUser` 在 `AdminController.java:96-101` 会调用 `getCurrentPrincipal()` 并做 ABAC 判断），`listUsers` 完全没有这一层。

### 依据 2：全局路由规则仅为 authenticated

`agent-qr-web/src/main/java/org/example/agent_qr/web/config/SecurityConfig.java:48-58`

```java
.requestMatchers("/api/auth/login", "/api/auth/register", "/api/auth/refresh").permitAll()
.requestMatchers("/ws/**", "/ws/info").permitAll()
.requestMatchers("/api/admin/**").authenticated()        // ← 设计要求 hasRole("ADMIN")
.requestMatchers("/api/knowledge/**").authenticated()
...
```

设计文档 §3.2.12 的路由表要求 `/api/admin/**` 使用 `hasRole("ADMIN")`，实现被放宽为 `authenticated()`。

### 依据 3：口令哈希随响应外泄

`agent-qr-user/src/main/java/org/example/agent_qr/user/entity/SysUser.java:33-38`

```java
/**
 * 密码，BCrypt 加密后的密文。
 */
private String password;
```

字段上无 `@JsonIgnore`、无 `@JsonIgnoreProperties`、无自定义序列化器。交叉验证：

```bash
grep -rn "@JsonIgnore" --include=*.java . | grep -v target
# 零命中
```

结合依据 1、2，`Result<IPage<SysUser>>` 会把 `password` 字段原样序列化返回。

### 依据 4：同类接口的对照

`AdminController` 的其他方法（`createUser`、`updateUser`、`updateUserStatus`）均有 `getCurrentPrincipal()` + ABAC 校验，说明"加校验"是本模块的既有惯例，`listUsers` 属于遗漏而非有意设计。

---

## 三、影响范围

1. **横向信息泄露**：普通用户可获取全站用户的用户名、真实姓名、邮箱、手机号、角色、部门、密级、职级、可访问域等全部属性——恰好是 ABAC 鉴权所依赖的全部字段，可被用于精准构造越权请求。
2. **凭据泄露**：BCrypt 哈希外泄，弱口令可离线爆破；BCrypt strength=12 虽提高成本，但无法阻止针对弱口令的字典攻击。
3. **与文档 07 叠加**：若攻击者同时利用刷新令牌缺陷进一步提权，风险面扩大。
4. **推翻复盘报告自评**：复盘报告称"权限管控已跑通"，该结论在本接口上不成立。

---

## 四、修复方向

1. **立即加权限校验**（二选一，建议都做）：
   - 在 `listUsers` 上加 `@PreAuthorize("hasRole('ADMIN')")` 或 `@PreAuthorize("@abac.canModifyUser(principal, #id)")` 类的判定；
   - 将 `SecurityConfig.java:52` 的 `/api/admin/**` 改为 `hasRole("ADMIN")`，与设计文档 §3.2.12 对齐。
2. **阻断口令外泄**（建议双保险）：
   - 给 `SysUser.password` 加 `@JsonIgnore`；
   - 更稳妥的做法是不要在 Controller 直接返回实体，改用不含敏感字段的 VO/DTO，避免后续新增敏感字段时再次遗漏。
3. **补充回归测试**：本接口若有一条"普通用户访问应返回 403"的用例，该缺陷不会存活至今——参见文档 33（全仓库零测试）。
