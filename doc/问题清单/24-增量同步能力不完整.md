# 24 · 增量同步能力不完整

> **严重程度**：🟡 中
> **所属模块**：agent-qr-datasource（JdbcConnector、RestApiConnector、S3Connector）
> **设计依据**：《系统详细设计说明书》§8.7.2 / §8.7.3 / §8.7.4（各连接器的 fullSync / incrementalSync）
> **核查日期**：2026-10-06
> **核查方式**：静态代码分析（未编译、未运行）

---

## 一、问题描述

三个连接器的增量同步能力均与设计文档存在差距，且**差距方向不一致**（有的缺失、有的超出设计）：

| 连接器 | 设计 §8.7.x 要求 | 实际状态 | 评价 |
|---|---|---|---|
| JDBC | 遍历 `tableNames` 多表做游标增量 | 只支持**单表**（`config.get("tableName")`） | ❌ 弱于设计 |
| JDBC | 游标分页增量 | 有真游标（`WHERE cursorField > ? ORDER BY ... ASC`），但**无分页/批次**，仍一次性物化 | ⚠️ 部分 |
| REST | 游标分页翻页增量 | 增量**只发一次 GET**，无翻页循环 | ❌ 弱于设计 |
| REST | — | 全量翻页有 `maxPages = 100` 硬编码静默上限 | ⚠️ 静默截断 |
| S3 | 增量"简化示例"直接调 fullSync | 真实实现了 `lastModified > cursorTime` 过滤 | ✅ 强于设计 |

另外，REST 全量同步完成后固定返回 `nextCursor = null`，导致下一次同步仍会走全量——增量机制在 REST 侧实际无法生效。

---

## 二、推断依据

### 依据 1：JDBC 增量只支持单表

`agent-qr-datasource/src/main/java/org/example/agent_qr/datasource/connector/JdbcConnector.java:158-173`

```java
String tableName = (String) config.get("tableName");      // 单表
...
// WHERE cursorField > ? ORDER BY cursorField ASC
```

而 `fullSync` 走的是多表遍历（`:110-124` 的 `for (String table : tables)`）。因此首次全量同步能覆盖多表，后续增量只覆盖一张表——**多出的表在增量阶段永久不再更新**。

### 依据 2：JDBC 增量无分页，仍全量物化

`JdbcConnector.java:165,174-187`：`List<Map<String, Object>> allRows = new ArrayList<>()` 后 `while (rs.next())` 逐行累加，与全量路径同一模式，无 `setFetchSize` / 批次消费。

### 依据 3：REST 增量只请求一次

`agent-qr-datasource/.../connector/RestApiConnector.java:122-132`

```java
// incrementalSync: 发出一次 GET，传入 lastCursor
```

对比 `fullSync`（`:66-100`）中存在 `X-Next-Cursor` 翻页循环——增量路径没有对应的循环结构，因此单次响应之后的分页数据被丢弃。

### 依据 4：REST 全量有 100 页静默上限

`RestApiConnector.java:66-69`

```java
int maxPages = 100; // 安全上限
while (page < maxPages) { ... }
```

超过 100 页的数据被静默丢弃，无任何日志或标记（命中上限时循环正常结束，调用方看到的是"同步成功"）。这与文档 23 的"异常被吞"叠加，进一步降低可观测性。

### 依据 5：S3 增量优于设计

`S3Connector.java:165-180` 按 `lastModified > cursorTime` 过滤，是真实实现；而设计文档 §8.7.4（说明书 3701 行）的增量是"简化示例"，直接调用 `fullSync`。这一项**实现强于设计**，属正面偏差。

### 依据 6：REST 全量不产出游标

`RestApiConnector.java:108`：全量同步固定返回 `nextCursor = null`，因此下一次同步无法进入增量模式，只能再次全量。这使得 REST 增量代码路径实际上难以被触发。

---

## 三、影响范围

1. **数据新鲜度不一致**：JDBC 多表数据源中，非 `tableName` 指定的表在首同步后不再更新——表现为"某些表的数据一直停留在首次同步的时间点"。
2. **REST 数据源等同全量**：因依据 3、6，REST 增量链路实际不可用，每次同步都是全量，性能与源系统压力都受影响（与文档 21 的性能问题叠加）。
3. **静默丢数据**：REST 的 100 页上限会静默丢弃数据，且同步记录显示成功。
4. **配置语义不明**：`connectionConfig` 的 JSON 结构未在代码中定义 schema（键名靠约定：`tableName` / `tableNames` / `cursorField` / `bucketName`），易出现配置与实际不符却无报错的情况。

---

## 四、修复方向

1. **JDBC 增量支持多表**：与 `fullSync` 对齐，遍历 `tableNames`，每张表各自维护游标。
2. **JDBC 增量加分页/流式**：与文档 21 的流式改造一并实施。
3. **REST 增量补翻页循环**：复用 `fullSync` 的 `X-Next-Cursor` 逻辑。
4. **REST 全量返回真实游标**：全量完成后应记录最后一次的分页游标（或时间戳），使下一次能走增量。
5. **`maxPages` 上限改为可配置并告警**：命中上限时应记录 WARN 并在同步记录中标记"结果被截断"，而非静默成功。
6. **定义 `connectionConfig` 的 schema**：建议用 DTO + `@Valid` 校验，替代当前的 `Map<String,Object>` 约定（这也正是复盘报告 §3 问题 2 指出的"接口靠文档描述"问题）。

---
