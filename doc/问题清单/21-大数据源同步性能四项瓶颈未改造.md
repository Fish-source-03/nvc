### 补充发现：批量攒批未减少 HTTP 往返（第 ⑤ 项）

`BatchEmbeddingService` 确实做了攒批（`:104-108` 的 `poll` + `drainTo`），但底层 `OllamaEmbeddingProvider.embedBatch()` 是**逐条循环调用**：

`agent-qr-rag/.../provider/ollama/OllamaEmbeddingProvider.java:67-73`

```java
@Override
public List<float[]> embedBatch(List<String> texts) {
    List<float[]> results = new ArrayList<>();
    for (String text : texts) {
        results.add(embed(text));       // 逐条 HTTP 调用
    }
    return results;
}
```

**三点必须说明的限定**（否则容易高估此项的严重性）：

1. **这不是实现缺陷**：设计 §6.2.4 给出的 `embedBatch` 示例代码**就是逐条循环**（说明书 2298-2304 行），P2 过程文档也写「Ollama 原生不支持批量」。代码与设计一致。
2. **但设计自身矛盾**：§17.8（说明书 6850 行）称 `embedBatch` "一次处理整批"、复杂度"O(N/B) 次 API 调用"——与 §6.2.4 的循环写法不可能同时成立（详见问题 39 的 A16）。
3. **并发已经存在**：`BatchEmbeddingService.consumerCount = Runtime.getRuntime().availableProcessors()`（`:64,71-78`），即 N 核并发消费，**不是串行排队**。所以"逐条"的代价被并发抵消了一部分。

**实测结论（2026-10-06）**：Ollama 0.35.0 的批量端点 `/api/embed` **存在且可用**（接受 `input` 数组）。因此改用批量端点**技术可行**，属于"对齐 §17.8 的设计意图"。

**收益已实测（对等条件对比）**：

| 并发度 | A. 当前实现（逐条） | B. 批量端点 | 提速 |
|---|---|---|---|
| 8 线程 × 8 条 | 18.2 s | 6.6 s | **2.7 倍** |
| **16 线程 × 16 条**（贴近真实配置） | 36.6 s | 24.7 s | **1.5 倍** |
| 单线程（**非对等，不可作决策依据**） | 72.0 s | 6.1 s | 11.7 倍 |

> ⚠️ **结论对并发度高度敏感**：并发越高、批量化收益越小。
> 原因：**Ollama 能并行处理并发请求**（实测 8 并发下单条均摊从 2173 ms 降到 334 ms，约 6.5 倍），
> 而当前实现**已经是 `consumerCount = CPU 核数` 的并发消费**——并发已经拿回了一部分吞吐。
> 因此**不要引用"11.7 倍"**（那是单线程下的数字）。

**按 1.5 倍推算的端到端收益**（取决于向量化占总同步耗时的比例）：

| 向量化占比 | 改造后总耗时 | 端到端收益 |
|---|---|---|
| 20% | 0.933 | 省 6.7% |
| 40% | 0.867 | 省 13.3% |
| 60% | 0.800 | 省 20% |

**未覆盖的因素**：本地 Ollama 的 HTTP/网络开销几乎为零，"256 次请求 vs 16 次请求"的差距未能体现；**若 Ollama 部署在远程，批量化收益会明显更大**。

**结论**：是否改造，取决于**向量化环节占总同步耗时的比例**（该比例须等 ①②③ 完成后才能测准）——已写入批次 05 任务 5.2.5，采用"先测后改"的方式决策。

## 三、影响范围

1. **准实时目标不达成**：100 万条量级的数据源首次同步耗时不可接受。
2. **内存风险**：瓶颈 ① 在全量装载时可能 OOM；与文档 11（PDF 全量加载）、文档 15（BM25 常驻内存索引）叠加，整体内存压力偏大。
3. **复盘报告的 P0 行动项未启动**：报告 §5.3 把"实施大数据源同步性能改造"列为 P0。
4. **抑制其他能力**：文档 12（结构化过滤）依赖 `kb_chunk_structured` 数据积累，而该表的填充速度正受本缺陷制约。

## 四、修复方向

方案文档 `doc/未来补充/大数据源同步性能改造方案.md` 已给出四管齐下的完整设计（含伪代码与压测方案）：

| 环节 | 改造 |
|---|---|
| ① | JDBC 连接器改流式读取（`setFetchSize` + 逐批消费） |
| ② | ETL 批量写入 MySQL（1000 条/批）+ 事件驱动解耦向量化 |
| ③ | 队列容量参数化并调大（建议 10000）+ 非阻塞降级 |
| ④ | ChromaDB 改 `addAll()` 批量写入 |

方案文档预估总耗时从 50 分钟降至 6-8 分钟。

**补充建议**：第 ⑤ 项——`OllamaEmbeddingProvider.embedBatch` 应改用 Ollama 的批量端点（若可用），否则攒批收益有限。此项不在原方案文档中，建议一并纳入。

**前置动作**：把队列容量参数化（当前硬编码），否则 ③ 无法配置化调整。
