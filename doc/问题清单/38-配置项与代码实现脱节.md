# 38 · 配置项与代码实现脱节（死配置汇总）

> **严重程度**：🟡 中
> **所属模块**：agent-qr-web（application*.yml）、agent-qr-common、agent-qr-rag、agent-qr-catalog、agent-qr-web-frontend
> **设计依据**：《系统详细设计说明书》§8.15.7、§8.15.3、§6.2.5.3；《项目复盘报告》§4 经验 1（要求为每个降级策略提供配置开关）
> **核查日期**：2026-10-06
> **核查方式**：静态代码分析（yml 键名 ↔ Java 读取点全仓库反向检索；未运行）

---

## 一、问题描述

配置文件中存在一批**有键无读取方**的配置项，其注释声称某项能力已开启，但实际没有任何 Java 代码消费它们。运维调整这些键不会有任何效果，且不会有任何报错。

这与文档 01（`@EnableScheduling` 缺失）、文档 16（Collection 隔离死代码）属于同一模式：**配置层呈现了能力已就绪的外观，实现层却未接线**。

> ⚠️ **范围澄清（重要）**：并非所有"无读取点"的键都是缺陷。
> 经复核，本项目存在**两类**：
> - **A 类（误导）**：注释声称会生效，实际不生效 → **是缺陷**，本文档处理对象
> - **B 类（诚实占位符）**：注释已标注"暂未使用""仅 X 可用" → **不是缺陷**，只是预留配置
>
> 本文档初版曾把 B 类也列为缺陷（如 `collection-prefix`），**该判断不准确，已更正**。详见下节分类表。

---

## 二、推断依据

### 配置项分类

**关键区分**：本文档初版把"无 Java 读取点"一律判为缺陷，**这是不准确的**。复核后发现应分为两类——**注释已如实标注为未使用/不可用的，属诚实的占位符，不是缺陷**；**注释声称会生效但实际无读取点的，才构成误导**。

#### A 类：误导性配置（注释声称生效，实际不生效）

| 配置键 | 位置 | 注释声称 | 实际情况 | 关联缺陷 |
|---|---|---|---|---|
| `agent-qr.routing.mode` | `application-p3.yml:41` | `域路由模式：keyword \| semantic \| auto` | 无 Java 读取；路由选择硬编码在 `ChatQueryService.java:328-351` | 本文件 |
| `agent-qr.embedding.auto-dimension-check` | `application-p3.yml:53` | `启动时自动检测向量维度一致性` | 无读取；`ensureCollection()` 恒返回 true | 文档 16 |
| `agent-qr.cache.max-size` | `application-p2.yml:61-63` | `最大缓存条数` | 无读取；`CaffeineConfig.java:33-34` 硬编码 10000 | 本文件 |
| `agent-qr.cache.ttl-hours` | 同上 | `缓存过期时间（小时）` | 同上 | 本文件 |
| `agent-qr.cqrs.read-replica-fallback-to-primary` | `application-p3.yml:38` | `初期从库不存在时回退到主库` | 该值**只被打印进日志**，不参与装配决策 | 文档 04 |
| `rag.embedding.write-to-chromadb` | `application-p1.yml:29` | `P1: 关闭 ChromaDB 写入，节省 API 调用` | 无读取；且**注释说关闭、值为 `true`**，自相矛盾 | 本文件 |
| `agent-qr.reranker.model` | `application-p2.yml:32` | `精排模型（P3 升级为 API 调用）` | 无读取；`RerankerService` 无 `@Value` | 文档 14 |
| `VITE_SSE_TIMEOUT` | `.env.development` | `P2 SSE 流式超时（毫秒，默认 5 分钟）` | 前端 `src/` 内无引用 | 本文件 |
| `VITE_TOKEN_REFRESH_AHEAD` | `.env.development` | `P2 Token 提前刷新时间` | 无引用；实际硬编码为 `60_000`（`api/index.ts:155`） | 本文件 |
| `VITE_SSE_MAX_RECONNECT` | `.env.development` | `P2 SSE 最大重连次数` | 无引用 | 本文件 |

#### B 类：诚实标注的占位符（**不是缺陷**）

| 配置键 | 位置 | 注释原文 | 结论 |
|---|---|---|---|
| `agent-qr.embedding.collection-prefix` | `application-p3.yml:52` | `ChromaDB Collection 前缀（暂未使用）` | 已如实标注"暂未使用"。**属预留配置**，仅需决定"何时启用 or 删除"，**不应按缺陷处理** |
| `agent-qr.provider.preferred-embedding` | `application-p3.yml:49` | `首选 Embedding Provider（仅 Ollama 可用）` | 注释已说明仅 Ollama 可用。**问题是与 `embedding.provider` 语义重叠**（详见文档 17），属配置冗余而非死配置 |

> **教训**：判断配置项是否为缺陷时，**必须先读注释**——注释已声明"暂未使用/仅 X 可用"的，是设计者的诚实标注，与"声称生效但不生效"有本质区别。

#### 对照：配置正确且生效的示例

`application-p1.yml:15` 的 `embedding.provider: ollama`（注释 `★ 使用本地 Ollama qwen3-embedding:4b（P2 配置: ollama.embedding.*）`）被 `ProviderFactory.java:29` 与 `OllamaEmbeddingProvider.java:27,30` 实际读取并生效——属于**配置与实现一致**的正例，不应出现在任何"死配置"清单中。

### 验证方式

对每个键名执行全仓库反向检索（`grep -rn "<key>" --include=*.java .`），**零命中**即判定为无读取方。例如：

```bash
grep -rn "routing.mode\|routingMode" --include=*.java .
# 零命中（仅 yml 与 doc 中有该字符串）
```

| 值 | 位置 | 问题 |
|---|---|---|
| 阻塞队列容量 2000 | `BatchEmbeddingService.java:46` | 硬编码，无法配置（改造前需先参数化，见文档 21） |

### 复盘报告要求的降级开关未落地

《项目复盘报告》§4 经验 1 明确要求："在 `application.yml` 中为每个降级策略提供开关配置，运维时可按环节灰度关闭"。

实际配置中只有零散的三个全局键（`circuit-breaker`、`dlq.max-retries/backoff-base`、`provider.auto-failover`），**没有任何按环节（解析/切片/向量化/写入/删除/ETL）的降级开关**。

## 三、影响范围

1. **运维陷阱**：改配置无效果，且无报错。排查时会浪费大量时间确认"配置到底生效了没有"。
2. **能力虚标**：`collection-prefix`、`auto-dimension-check`、`routing.mode` 这些键的存在，让评审者以为 P3 的相关能力已实现并可配置。
3. **灰度能力缺失**：复盘报告明确要求的"按环节灰度关闭"降级策略没有实现，出问题时无法通过配置快速止血——只能改代码重新发布。
4. **注释与取值矛盾会增加误判**：`rag.embedding.write-to-chromadb` 的注释与值相反，运维据此判断会得到错误结论。

---

## 四、修复方向

1. **按 A / B 两类分别处理**：
   - **A 类（误导性）必须处理**——要么接通，要么删除并修正注释，不能继续保持"声称生效但不生效"的状态：
     - 接线：`agent-qr.cache.*` 改为 `@Value` 读取（成本极低）；`agent-qr.reranker.model` 随文档 14 的选型决策接通；`read-replica-fallback-to-primary` 随文档 04 接通
     - 删除或接通：`routing.mode`（若短期不实现开关，应删除并修正注释）
     - 修正矛盾：`rag.embedding.write-to-chromadb` 的注释与取值必须一致
   - **B 类（诚实占位符）按既定决策处理即可**——`collection-prefix` 属预留配置，接通即可（已确认的 38 号决策「能接线就接线」），**不必按缺陷对待**；`preferred-embedding` 的冗余问题见文档 17
2. **反向补齐硬编码值**：把队列容量、REST 翻页上限、Reranker 权重、SSE 刷新时间参数化——前两项是文档 21、24 修复的前置动作。
3. **修正矛盾注释**：`application-p1.yml:29` 的注释与取值需对齐。
4. **落实复盘经验 1**：为事件链的每个环节（解析/切片/向量化/ChromaDB 写入/删除/ETL）提供独立的降级开关，默认开启，支持灰度关闭。
5. **建立防漂移机制**：建议在 CI 中增加一个简单检查——扫描 yml 中的所有键，确认每个键在全仓库存在读取点（可容忍白名单），防止再次积累。

---

## 五、核查边界

- 采用"键名全仓库反向检索"判定无读取方。若某键通过 `Environment` / `@ConfigurationProperties` 的宽松绑定（如 `agent-qr.cache` 绑定到 POJO）间接使用，可能存在漏判——已对每个键单独检索，未发现此类间接绑定。
- 未检查是否存在外部配置中心（Nacos 等）覆盖——仓库中未见相关依赖。
- 未在实际部署环境中验证这些键是否生效。
