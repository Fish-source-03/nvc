# 33 · 前后端契约断裂（筛选参数被静默丢弃 + 登出接口 404）

> **严重程度**：🟠 中高
> **所属模块**：agent-qr-web-frontend、agent-qr-knowledge、agent-qr-user、agent-qr-rag、agent-qr-auth
> **设计依据**：《p2-frontend-design.md》中的域选择器与 ABAC 筛选设计；《系统详细设计说明书》§3.2.13、§5.2.1
> **核查日期**：2026-10-06
> **核查方式**：静态代码分析（前端 API 定义 ↔ 后端 Controller 签名逐一比对；未运行、未发请求）

---

## 一、问题描述

核查发现 4 处前端已实现、后端未接收的契约断裂。由于 Spring 对未声明的查询参数**静默忽略**，这些缺陷**不报错、只是没效果**——用户看到 UI 上有筛选控件，操作后数据毫无变化。

| # | 前端发送 | 后端实际接收 | 后果 |
|---|---|---|---|
| 1 | 知识库列表 `domain` / `sensitivityLevel` | 仅 `page` / `size` | "业务域/密级"筛选器无效 |
| 2 | 用户列表 `department` / `title` | 仅 `page` / `size` / `keyword` | "部门/职级"筛选器无效 |
| 3 | SSE 问答 `domain` | 仅 `query` / `conversationId` | 域选择器无法限定检索范围 |
| 4 | `POST /api/auth/revoke` | 端点不存在 | 登出时必发一次失败请求 |

第 3 项与文档 09（问答域鉴权缺失）是同一问题的两面：前端有控件、后端不接收、ABAC 不校验。

---

## 二、推断依据

### 断裂 1：知识库列表筛选

前端：`agent-qr-web-frontend/src/api/knowledge.ts:17-18` 传 `domain` / `sensitivityLevel`；`src/views/knowledge/KnowledgeView.vue:43-45` 从筛选控件取值。

后端：`agent-qr-knowledge/.../controller/KnowledgeController.java:60-63`

```java
@GetMapping("/documents")
public Result<...> listDocuments(
        @RequestParam(defaultValue = "1") Integer page,
        @RequestParam(defaultValue = "10") Integer size) { ... }
```

无 `domain` / `sensitivityLevel` 参数。

### 断裂 2：用户列表筛选

前端：`src/api/user.ts:5`、`src/views/user/UserManageView.vue:38-39` 传 `department` / `title`。

后端：`agent-qr-auth/.../controller/AdminController.java:74-78`

```java
public Result<IPage<SysUser>> listUsers(
        @RequestParam(defaultValue = "1") Integer page,
        @RequestParam(defaultValue = "10") Integer size,
        @RequestParam(required = false) String keyword) { ... }
```

无 `department` / `title`。

### 断裂 3：SSE 问答的域参数

前端：`src/api/chat.ts:38` 的 `askStream` 请求体含 `domain`。

后端：`agent-qr-rag/.../controller/ChatController.java:75-83` 只取 `query` / `conversationId`；服务层签名 `ChatQueryService.java:181` 亦无 domain。

`p2-frontend-design.md:852` 明确描述"域选择器限定检索范围"。

### 断裂 4：登出接口

前端：`src/api/auth.ts:19-21` 调用 `POST /api/auth/revoke`；`src/stores/auth.ts:190-195` 在 logout 中调用。

后端：`agent-qr-auth/.../controller/AuthController.java` 的全部映射仅 `:41 /login`、`:53 /register`、`:68 /refresh`、`:79 /info`——**无 `/revoke`**。

（该断裂的完整分析另见文档 08。）

### 补充观察：前后端确实在其他地方对齐良好

同一批核查确认，除上述 4 处外，**其余 30 余个接口的路径、方法、请求体、响应结构均一致**（含 `IPage` 分页结构、`todayPositive/todayNegative` 字段名、SSE `done` 事件的 `answer/conversationId/messageId/sources` 载荷）。因此这些断裂属**局部遗漏**，不是系统性的契约管理缺失——但恰恰因为大部分是对的，这 4 处更难被发现。

---

## 三、影响范围

1. **"假功能"最伤信任**：用户操作筛选器没有反应，且没有任何提示。相比"报错"，静默无效更难察觉、更易被误认为"系统没数据"。
2. **ABAC 能力被架空**：断裂 1、3 涉及业务域与密级筛选，这些都是 ABAC 设计中的核心维度。UI 上做了控件，等于向用户承诺了能力。
3. **登出体验受损 + 安全问题**：见文档 08。
4. **测试缺失放大问题**：前后端均无自动化测试（见文档 37），接口契约变化无任何拦截机制。

---

## 四、修复方向

1. **逐个补齐后端参数**：
   - `KnowledgeController.listDocuments` 增加 `domain` / `sensitivityLevel` 参数并透传到查询；
   - `AdminController.listUsers` 增加 `department` / `title` 参数；
   - `ChatController` 的 `/ask` 与 `/ask/stream` 解析 `domain` 并接入 ABAC（与文档 09 一并修复）。
2. **补 `/api/auth/revoke` 端点**（见文档 08）。
3. **建立契约测试**：这 4 处断裂之所以能长期存在，是因为没有任何机制验证"前端调用的参数后端是否真的接收"。建议：
   - 后端补 `@Valid` 与参数白名单校验（对未知参数可选择报错而非静默忽略）；
   - 或在 CI 中做一次"前端 API 定义 ↔ 后端 Controller 签名"的比对。
4. **短期自检**：建议全局搜索前端 `params` 对象的所有键，逐一确认后端是否声明。

---

## 五、核查边界

- 静态比对，未实际发起请求验证参数是否真被忽略。
- Spring 对未声明参数的默认行为是忽略（`@RequestParam` 未声明即不绑定），本结论基于该既有语义。
- 未检查前端是否存在对这些参数的客户端过滤兜底（从代码看筛选逻辑完全依赖后端返回）。
- 前端 P3 新增页面（规则管理、知识图谱等）与后端的契约未纳入本次比对范围（其设计文档依据为 `doc/p3-prompt.md`，非正式设计说明书）。
