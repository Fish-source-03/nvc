# 27 · 知识库软删切片漏出（`selectByDocumentId` 缺 `deleted = 0`）

> **严重程度**：🟡 中
> **所属模块**：agent-qr-knowledge（ChunkMapper、DocumentQueryService、KnowledgeController）
> **设计依据**：《系统详细设计说明书》§8.12 文档删除一致性设计 v2（检索侧应过滤已删除切片）
> **核查日期**：2026-10-06
> **核查方式**：静态代码分析（未编译、未运行）

---

## 一、问题描述

文档删除采用软删除（`@TableLogic` + `deleted` 列）。MyBatis-Plus 的 `@TableLogic` **只对框架自动生成的 SQL 生效，对 `@Select` 手写 SQL 不生效**。

`ChunkMapper.selectByDocumentId` 是手写 SQL 且**未带 `deleted = 0` 条件**，因此该查询会返回该文档下**已被软删除的全部切片**。该查询由 `DocumentQueryService.getChunks` 调用，并通过 `KnowledgeController` 的 `/documents/{id}/chunks` 接口对外暴露。

后果：文档删除后，其切片仍可被查看；同一模块内的另一条读取路径（`ChunkIndexableTextProvider`）走 LambdaQueryWrapper 却是正确过滤的——**两条路径行为不一致**。

---

## 二、推断依据

### 依据 1：手写 SQL 未带软删条件

`agent-qr-knowledge/src/main/java/org/example/agent_qr/knowledge/mapper/ChunkMapper.java:39-40`

```java
@Select("SELECT * FROM kb_chunk WHERE document_id = #{documentId} ORDER BY chunk_index")
List<Chunk> selectByDocumentId(@Param("documentId") Long documentId);
```

对照同文件的软删除方法 `:47-48`：

```java
// chunkMapper.softDeleteByDocumentId —— 把 deleted 置 1
```

即该表确实使用 `deleted` 列做逻辑删除，而依据 1 的查询没有排除已删除行。

### 依据 2：实体确实声明了逻辑删除

`agent-qr-knowledge/.../entity/Chunk.java:86-87`

```java
@TableLogic
private Integer deleted;
```

`@TableLogic` 只影响 MyBatis-Plus 自动生成的 CRUD（如 `selectById`、`selectList`），对手写 `@Select` 无约束——这是本缺陷的技术根因。

### 依据 3：查询被 Service 与 Controller 暴露

- `agent-qr-knowledge/.../service/DocumentQueryService.java:71-73` 调用 `selectByDocumentId`；
- `agent-qr-knowledge/.../controller/KnowledgeController.java:92` 暴露为 `GET /api/knowledge/documents/{id}/chunks`。

### 依据 4：同模块另一条路径行为相反

`agent-qr-knowledge/.../service/ChunkIndexableTextProvider.java:44-46` 使用 `LambdaQueryWrapper`，由 MyBatis-Plus 自动追加 `deleted = 0`，因此过滤是**正确**的。

两条读取路径行为不一致，说明这不是"有意设计"，而是遗漏。

### 依据 5：与设计文档矛盾

§8.12（说明书 4819 行附近）注释写明"检索时自动过滤已删除切片"。`selectByDocumentId` 违背了这一约定。

---

## 三、影响范围

1. **删除语义不完整**：用户删除文档后，通过切片接口仍能读到内容——**软删除对用户不可见**。
2. **潜在的检索污染**：若未来有其他检索路径复用 `selectByDocumentId`（当前仅 `getChunks` 使用），会把已删除切片带回检索结果。
3. **数据一致性表象**：文档列表里看不到该文档，但切片能查到，用户会认为"删除没删干净"。
4. **与文档 29 关联**：孤儿向量扫描的输入查询（`selectAllReadyChunks`）是带 `deleted = 0` 的，恰好**漏掉**了本缺陷涉及的那批切片——两个问题在"软删切片的处理"上方向相反。

---

## 四、修复方向

1. **给手写 SQL 补条件**（最小改动）：
   ```java
   @Select("SELECT * FROM kb_chunk WHERE document_id = #{documentId} AND deleted = 0 ORDER BY chunk_index")
   ```
2. **排查同类问题**：建议对 `ChunkMapper` / `DocumentMapper` 中**所有**手写 `@Select` 做一次审查，确认是否都带了 `deleted = 0`——`@TableLogic` 的"只对自动 SQL 生效"是一个容易反复踩的坑。已知 `ChunkMapper.java:59,65` 的裸 SQL 也依赖 `status` 列，建议一并核对。
3. **长期建议**：考虑用 LambdaQueryWrapper 替代手写 SQL，让 `@TableLogic` 自动生效；或在 Mapper 层统一封装。
4. **补测试**：至少一条"删除文档后，切片接口应返回空或 404"的用例。

---

## 五、核查边界

- 静态分析，未实际调用该接口验证返回内容。
- 未连接数据库确认 `kb_chunk` 表中 `deleted = 1` 的记录量与分布。
- 未排查 `DocumentMapper` 是否存在同类问题（本次仅核查了 `ChunkMapper` 与 `DocumentMapper` 中设计文档点名的方法）。
