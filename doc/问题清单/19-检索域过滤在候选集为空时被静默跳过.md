# 19 · 检索域过滤在候选集为空时被静默跳过

> **严重程度**：🟠 中高（安全相关）
> **所属模块**：agent-qr-rag（HybridRetriever）
> **设计依据**：《系统详细设计说明书》§8.11.3 HybridRetriever 集成（候选集为空应直接返回空）
> **核查日期**：2026-10-06
> **核查方式**：静态代码分析（未编译、未运行）

---

## 一、问题描述

`HybridRetriever` 的域过滤使用了一个**双重守卫条件**：只有当"指定了域"**且**"候选 chunkId 列表非空"时，才执行过滤。

设计 §8.11.3（说明书 4720-4722 行）明确要求：当候选集为空时，应**直接返回空结果**，因为"域内没有匹配数据"意味着"没有答案"。

当前实现把空候选集解释为"无需过滤"，于是**跳过过滤、退化为全库检索**。结果是：当用户在某个业务域下提问、而该域恰好没有结构化数据时，系统会返回**其他业务域的内容**——这既是正确性问题，也是越权隐患（与文档 09 的问答域鉴权缺失叠加）。

---

## 二、推断依据

### 依据 1：守卫条件与设计相反

`agent-qr-rag/src/main/java/org/example/agent_qr/rag/retriever/HybridRetriever.java:104-116`

```java
// Step 1.5: 域后过滤 — 仅当指定了域时才过滤
boolean hasDomainFilter = domain != null && !domain.isBlank();
if (hasDomainFilter && !candidateChunkIds.isEmpty()) {          // ← 第二个条件导致空集时跳过
    Set<Long> allowedIds = new HashSet<>(candidateChunkIds);
    semanticResults = semanticResults.stream()
            .filter(doc -> doc.getChunkId() != null && allowedIds.contains(doc.getChunkId()))
            .toList();
    keywordResults = keywordResults.stream()
            .filter(doc -> doc.getChunkId() != null && allowedIds.contains(doc.getChunkId()))
            .toList();
    log.debug("域后过滤: domain={}, allowedIds={}, semanticAfter={}, keywordAfter={}",
            domain, allowedIds.size(), semanticResults.size(), keywordResults.size());
}
```

- `candidateChunkIds` 来自 `structuredFilterService.filterChunkIds(domain, filterConditions)`（`HybridRetriever.java:97`）；
- 若该域下 `kb_chunk_structured` 表无数据，返回空列表；
- 此时 `!candidateChunkIds.isEmpty()` 为 false，整个 `if` 块被跳过，**`semanticResults` 与 `keywordResults` 保持全量召回结果**，随后直接进入 RRF 融合。

### 依据 2：设计文档的明确要求

《系统详细设计说明书》§8.11.3 描述"MySQL 前置结构化过滤"的集成方式时要求：`candidateChunkIds` 为空时**直接返回空结果**（说明书 4720-4722 行），而不是放弃过滤。

### 依据 3：无任何日志或告警

该分支被跳过时，除 `log.debug` 外无任何提示；`log.debug` 本身也在被跳过的块内，因此**运行期完全静默**——运维无法从日志中发现"域过滤未生效"。

### 依据 4：与域鉴权缺失叠加

文档 09 已确认 `ChatController` 未做 ABAC 域校验、`canQueryDomain` 无调用方。因此当前"按域过滤"是唯一的域隔离手段，而本缺陷使该手段在特定条件下失效。

---

## 三、影响范围

1. **跨域结果泄露**：用户在域 A 下提问，可能收到域 B 的内容。在 ABAC 语境下这属于越权访问。
2. **答案错误**：用户以为在限定范围内检索，实际是全局检索，答案的业务口径可能完全不同。
3. **静默失效**：无日志、无异常、无告警，问题难以被察觉。
4. **与偏差 2 关联**：结构化过滤链路的消费端本就是"接了线没通电"（文档 12），本缺陷是其上的第二层问题——即便将来接通了提取器，这个守卫条件仍会导致空集场景出错。

---

## 四、修复方向

1. **修正守卫逻辑**：把空候选集的处理从"跳过过滤"改为"返回空结果"，与设计 §8.11.3 对齐：
   ```java
   if (hasDomainFilter) {
       if (candidateChunkIds.isEmpty()) {
           log.warn("域 {} 无结构化候选数据，返回空结果", domain);
           return List.of();
       }
       // 正常过滤...
   }
   ```
2. **补充可观测性**：该分支命中时应有 WARN 级日志或指标，便于发现"某域长期无数据"。
3. **考虑降级策略的语义**：若业务上确实需要"域内无数据时回退全局"，应作为**显式配置**存在，并在回答中提示用户"已扩大检索范围"，而不是静默扩大。
4. **与文档 09 一并修复**：域隔离在问答链路上需要"入口鉴权 + 检索过滤"双保险。

---

## 五、核查边界

- 静态分析，未运行检索、未构造"域内无结构化数据"的场景。
- 未连接数据库确认 `kb_chunk_structured` 表的实际数据分布——该表覆盖率决定本缺陷的触发频率。若该表整体为空（很可能，参见文档 12 的分析），则**所有带域的查询都会走到这个分支**，影响面会显著放大。
- 未评估 `routing.getPrimaryDomain()` 返回 null 的频率（null 时 `hasDomainFilter` 为 false，同样不做过滤，属设计预期行为）。
